# Архитектура frontend (frontend.md)

Документ верхнего уровня: слои, контракты и связи. Без деталей реализации.
Источники: `ui.md` (блоки, состояния, форматы данных), `api.md` (контракт данных),
`domain.md` (бизнес-правила — только по ссылке), `specification.md` (требования).

Приложение — одна desktop-страница: дашборд из 11 блоков (`ui.md`). Клиент не
считает бизнес-метрики: значения, Δ, доли и вклады приходят с сервера одним
ответом (`api.md`).

Базовый стек: **Next.js (App Router) + TypeScript**; серверное состояние —
TanStack Query (кэш, stale-while-revalidate). Контракты слоёв ниже от выбора
библиотек не зависят. Обоснованный выбор остальных библиотек — раздел 13.

---

## 1. Принципы

- **Один запрос — весь дашборд.** `POST /api/v1/dashboard` вызывается один раз на
  набор фильтров; блоки не делают собственных запросов (`api.md`).
- **Однонаправленные зависимости.** `pages → widgets → components`;
  доступ к данным — только `widgets → hooks → api`. Обратных и боковых импортов нет.
  `pages` импортирует только `widgets` — никаких прямых импортов `components`.
- **URL — источник правды глобальных фильтров** (период, сегмент). Всё остальное
  (активный датасет, hover) — локальное состояние виджета. Локальное — значит
  эфемерное: сброс на дефолт при перезагрузке страницы — ожидаемое поведение,
  персистентности (URL / localStorage / cookie) для табов нет.
- **Единый контракт состояний блока**: loading / refreshing / error / empty / data.
  Каждый блок отображает своё состояние независимо от остальных.
- **Данные — сырые числа, форматирование — на компоненте** (`ui.md`, «Сквозные
  правила отображения чисел»).
- **Бизнес-логики на клиенте нет.** Расчёты метрик, Δ, вкладов и ранжирование —
  на сервере; на клиенте — доступ к данным, состояния и отображение.
- **Read-only клиент.** Мутаций нет; кэш только читается и перезапрашивается.

## 2. Слои

| Слой | Роль | Может | Не может |
|---|---|---|---|
| `pages` (папка `app/`) | Страница: маршруты Next.js, композиция виджетов, провайдеры | `layout.tsx`/`page.tsx`, `next/navigation`, провайдер `DashboardQuery`-контекста, хуки `hooks/app` | Импортировать `components`, `api`, доменные/UI-хуки; рендерить контент блоков, вызывать API, знать DTO |
| `widgets` | Блоки `ui.md` (1 блок = 1 виджет) + инфраструктурные виджеты страницы (toolbar, toasts) | Доменные хуки (`hooks/domain`), app-хуки (`hooks/app`), UI-хуки (`hooks/ui`), локальные состояния, конфиг блока | Импортировать `api/*`, `next/*`, вызывать fetch, знать о кэше |
| `hooks` | Хуки приложения: `app/` — граница URL, `ui/` — логика представления, `domain/` — доступ к данным | Читать `DashboardQuery` из контекста, управлять кэшем, `useDisclosure`, `useAnimatedCounter` | Содержать JSX, форматировать значения, считать метрики |
| `components` | Render-only элементы: примитивы, элементы данных, графики | Props in → JSX out, форматирование, анимации, UI-хуки (`hooks/ui`) | Обращаться к доменным и app-хукам (`hooks/domain`, `hooks/app`), `api`, URL, контекстам |
| `api` | Детали API за хуками: HTTP-клиент, типы DTO `api.md`, маппинг DTO → app-типы | POST-запрос, приведение enum'ов, типизация ошибок | Знать о React, кэше и состояниях UI |
| `utils` | Чистые хелперы без React и домена | Форматирование чисел/дат, раскрытие границ дня, общие функции (`formatDate`, `clamp`) | React, состояние, домен, константы, URL-контракт |
| `types` | Только типы данных (DTO ответов, app-типы по `ui.md`: `Delta`, `Dataset`, `Contribution`) | Объявлять структуры | Рантайм-код, значения, контракты модулей |
| `interfaces` | Публичные контракты модулей: границы, экспортируемые API (`BlockState<T>`, `DashboardQuery`) | Объявлять контракты | Реализацию, константы, рантайм-логику |
| `configuration` | Конфигурация и константы: дефолты, пресеты, env-настройки | Типизированные константы (`DEFAULT_PERIOD_PRESET`, `DEFAULT_SEGMENT`) | Логику, расчёты, побочные эффекты |

UI-слои — ровно четыре: `pages`, `widgets`, `components`, `hooks`. Остальные —
папки деталей и слои без зависимостей.

Структура каталогов (ориентир):

```
frontend/src/
  app/                  # layout.tsx, page.tsx — страница: композиция виджетов,
                        #   провайдер DashboardQuery-контекста; layout минимален,
                        #   страница одна
  widgets/              # kpi/, manager-rating/, ..., toolbar/, toasts/ — по виджету
  hooks/                # app/, ui/, domain/ — все хуки приложения
  api/                  # client, dto (api.md), mappers (DTO → app-типы), errors
  components/           # ui/, data/, charts/ — render-only (приватная библиотека виджетов);
                        #   категории ui/, data/, charts/ — по назначению элемента,
                        #   шаблонов страниц здесь нет
  utils/                # format.ts, dates.ts — чистые хелперы (в т.ч. раскрытие границ дня)
  types/                # dto.ts, metrics.ts, periodPresetType.ts — только типы данных (app-типы по ui.md)
  interfaces/           # blockState.ts, dashboardQuery.ts — публичные контракты
  configuration/        # dashboard.ts (дефолты периода/сегмента), env.ts
```

Именование файлов: компоненты, виджеты — с большой буквы
(`PeriodPresetToolbar.tsx`, `Layout.tsx`/`Page.tsx` — но в App Router Next.js
имена `layout`/`page` фиксированы фреймворком и исключение); хуки, утилиты,
типы и конфиг — camelCase (`useDashboardQuery.ts`, `periodPresetType.ts`).

**Один файл — одна сущность.** Сервисы, утилиты, типы, интерфейсы, хуки и
константы живут каждый в своём файле: имя файла = имя сущности, содержимое =
только эта сущность (+ её docstring). Исключение — компонент: в файле
компонента допустимо объявить его props-тип (`PeriodPresetToolbarProps`);
выносить props отдельным файлом и переиспользовать их чужими компонентами
не нужно — props-тип это деталь конкретного компонента. Общие типы — в
`types/`, общие контракты — в `interfaces/`.

## 3. Связи и правила зависимостей

```
        pages ──────► widgets ──────► hooks ──► api ──► backend
          (app/)          │                            (POST /api/v1/dashboard)
                          ▼
                      components
```

UI-слои — ровно четыре: `pages`, `widgets`, `hooks`, `components`. Рендер —
`pages → widgets → components`; данные — `widgets → hooks → api`; UI-хуки
(`hooks/ui`) доступны и `widgets`, и `components`. `pages` импортирует только
`widgets` и провайдер из `hooks/app`; `components` — приватная библиотека
виджетов.

Слои без зависимостей (используются любым слоем, но сами никого не
импортируют): `utils`, `types`, `interfaces`, `configuration`.

Запреты (закрепляются правилами линтера, import boundaries):

- `pages` импортирует только `widgets` и `hooks/app` (провайдер); `components`, `api`, доменные/UI-хуки — нет.
- `components` остаются render-only: никаких `hooks/domain/*`, `hooks/app/*`, `api`, `next/*`, URL и контекстов — только `utils`, `types`, `configuration` и `hooks/ui/*`.
- `widgets` не импортируют `api` и `next/*`; доступ к данным — только через `hooks/domain/*`, к фильтрам — через `hooks/app/*`. Прямого доступа виджетов к `DashboardQueryContext` нет: фильтры доходят до виджета только внутри `BlockState`.
- `hooks/ui/*` не импортируют `api`, `hooks/domain/*` и не знают о URL — чистые хуки логики представления.
- `hooks` — только TypeScript без JSX; не импортируют `widgets` и `components`.
- `api` не импортирует React и не знает о состояниях интерфейса.
- `utils` не импортируют React, `hooks`, `api`, `widgets`, `components` и не хранят константы — это `configuration/`.
- `configuration` — только значения (`as const`, простые объекты); логики, расчётов и побочных эффектов здесь нет.
- `types` — только данные; `interfaces` — только контракты. Смешивать их нельзя.
- Один файл — одна сущность: хук, сервис, утилита, тип, контракт, набор констант
  — отдельные файлы. Исключение — props-тип компонента: объявляется в файле
  самого компонента (`PeriodPresetToolbar.tsx` → `PeriodPresetToolbarProps`).
- `next/navigation` используется только в `hooks/app` (`useDashboardQuery`) и
  `pages` (корневой `layout.tsx` Next.js); UI-компоненты в `app/` не живут —
  `app/` содержит только `layout.tsx` и `page.tsx`.
- Никто, кроме app-level хука `hooks/app/useDashboardQuery.ts`, не читает и не пишет `searchParams`.

## 4. URL-контракт

Маршрут — `/`. Глобальные фильтры хранятся в `searchParams`:

| Параметр | Формат | Смысл |
|---|---|---|
| `from` | `YYYY-MM-DD` | Начало периода (календарный день, UTC) |
| `to` | `YYYY-MM-DD` | Конец периода, включительно |
| `segment` | `enterprise` / `mid-market` / `smb` | Сегмент клиента (`smb` — small and medium business, малый и средний бизнес); отсутствует — все сегменты |

```ts
type DashboardQuery = {
  from: IsoDate;                    // YYYY-MM-DD
  to: IsoDate;                      // YYYY-MM-DD
  segment: CustomerSegment | null;  // null — все сегменты
};
```

Правила:

- **Нормализация.** Отсутствующие или невалидные параметры приводятся к дефолту
  (пресет «30 дней», все сегменты; невалидный `from > to` нормализуется).
  Нормализация — часть хука `hooks/app/useDashboardQuery.ts`, не утилита: он знает
  контракт `DashboardQuery` и дефолты из `configuration/`.
- **Запись.** Смена периода или сегмента — клиентская навигация
  `router.replace` (без перезагрузки, без скролла, без засорения истории).
- **Пресеты** («Сегодня», «7 дней», «Этот месяц»…) вычисляются на клиенте в UTC;
  сервер получает готовые границы (`api.md`).
- **Границы дня** раскрываются в UTC-диапазон чистой функцией из `utils/dates.ts`:
  `from 00:00:00Z … (to + 1 день) 00:00:00Z` — полуинтервал `[from, to)`
  (`domain.md`, «Активный период»); верхняя граница исключается.
- В URL попадают только глобальные фильтры: активный датасет и прочие
  переключатели остаются локальным состоянием виджетов.

**Где лежат константы периода.** Набор пресетов — отдельный тип; константы —
типизированные значения в `configuration/`:

```ts
// types/periodPresetType.ts — пресеты периода (ui.md, «Период»);
// «произвольный период» — отдельный режим (from/to), а не пресет
export type PeriodPresetType =
  | 'today'
  | '7d'
  | '30d'
  | 'this-month'
  | 'last-month';
```

```ts
// configuration/dashboard.ts
import type { PeriodPresetType } from '../types/periodPresetType';

export const DEFAULT_PERIOD_PRESET: PeriodPresetType = '30d'; // пресет по умолчанию
export const DEFAULT_SEGMENT = null as const;                 // все сегменты
```

| Константа | Файл | Ответственность |
|---|---|---|
| `DEFAULT_PERIOD_PRESET` | `configuration/dashboard.ts` | Дефолтный пресет при невалидном/пустом URL |
| `DEFAULT_SEGMENT` | `configuration/dashboard.ts` | Дефолт при отсутствии `segment` |

| Не константа (ответственность кода) | Файл | Что решает код |
|---|---|---|
| Список пресетов («Сегодня», «7 дней»…) | `components/ui/PeriodPresetToolbar.tsx` | Какие пресеты показывает тулбар |
| Нормализация `from > to` | `hooks/app/useDashboardQuery.ts` | Как привести невалидный период (поменять местами / обнулить / отбросить) |
| Раскрытие границ дня | `utils/dates.ts` | `from 00:00:00Z … (to + 1 день) 00:00:00Z` |

**URL ↔ состояние: `hooks/app/useDashboardQuery.ts` — app-level hook,
единственная граница с `searchParams`.** Чтение и запись симметричны и живут в
одном модуле, чтобы контракт `searchParams` не разъезжался между двумя местами:

```ts
// hooks/app/useDashboardQuery.ts — импортируется только слоем app
export function useDashboardQuery(): {
  query: DashboardQuery;                    // поиск + валидация + нормализация
  setQuery: (next: DashboardQuery) => void; // router.replace с теми же правилами
};
```

Связка — в два шага, компонент тулбара остаётся render-only и только эмитит
события:

1. `page.tsx` вызывает хук, публикует `query` в контексте и передаёт
   `query`/`setQuery` в виджет `widgets/toolbar/`.

2. Виджет рендерит компонент `components/ui/PeriodPresetToolbar.tsx` плоскими
   пропсами и подписывается на его события (callback-пропсы); из события и
   текущего `query` он собирает новый `DashboardQuery` и вызывает `setQuery`:

```ts
// components/ui/PeriodPresetToolbar.tsx — render-only, наружу только события
type PeriodPresetToolbarProps = {
  activePreset: PeriodPresetType | null;  // null — режим «произвольный период»
  from: IsoDate;
  to: IsoDate;
  segment: CustomerSegment | null;

  onPresetSelect: (preset: PeriodPresetType) => void;
  onSegmentSelect: (segment: CustomerSegment | null) => void;
  onPeriodChange: (from: IsoDate, to: IsoDate) => void;
};
```

Компонент не знает ни `DashboardQuery`, ни `setQuery`, ни `searchParams` —
формат `searchParams` больше нигде не известен.

Бизнес-пороги (`isEmpty`, `delta: null`, минимальная выборка) frontend не
знает: `api` либо присылает значение, либо `null` / `400`; `—` рендерится по
правилам `ui.md`.

`app` через `parseDashboardQuery` получает `DashboardQuery` и публикует его в
контексте; hooks читают query из контекста и включают его в ключ кэша. Виджеты
к контексту не обращаются: **механизм распространения фильтров — цепочка
«URL → контекст → domain-hook → BlockState»**. Меняется URL → контекст
перерисовывает доменные hooks → хук перезапрашивает (или отдаёт кэш/предыдущий
период) → виджет получает обновлённый `BlockState` и перерисовывается. Единственный
источник правды — URL; контекст — канал доставки, а не второй источник.

Точнее по связям: контекст связывает **не уровни, а стороны** — провайдер
живёт в `pages` (`page.tsx`), потребители — `hooks/domain` и `hooks/app`.
Страница не знает о доменных хуках (запрет из раздела 3), доменные хуки не
знают о странице; контекст — граница между ними, поэтому допустимо, что
поставщик и потребитель контекста принадлежат разным слоям. Контракт
контекста (`DashboardQueryContext`) объявлен в `interfaces/`, реализация
провайдера — в `hooks/app`, потому что только `hooks/app` владеет
`searchParams`.

Аналогия — **инициализация контейнера**. `DashboardQueryContext` — объект
доменного уровня (контракт в `interfaces/`), такой же, как `BlockState`:
страница ничего о нём не знает при рендере, её роль — один раз создать и
наполнить («page — composition root»). Записью управляет `hooks/app`
(`setQuery` → `router.replace`), чтением — `hooks/domain`; сама страница
после публикации значения не передаёт и в распространении не участвует.
Правило независимости блоков сохраняется: контекст один, мутации его
значения — только через `hooks/app`.

## 5. Слой hooks

Все хуки приложения живут здесь; разделение — через подпапки:

```
hooks/
  domain/   # useKpi, useManagerRating, useTopCustomers, ... (11 блоков + useDashboard)
  ui/       # useDisclosure, useAnimatedCounter, useHoverGroup, ...
```

### domain/

Единственная точка, где виджеты касаются данных. Один хук на блок:

```
useKpi, useManagerRating, useManagerComparison, useTopCustomers,
useCustomerDynamics, useTimeSeries, useCategories, useTopProducts,
useRecentSales, useRefunds, useCancellations
```

Плюс базовый `useDashboard` — один на всё приложение: владеет запросом и
отдаёт `DashboardStatus` для виджета `widgets/toasts/`.

Правила:

- Все hooks работают с **одним кэшем** на ключ `[from, to, segment]`; селектор
  блока отдаёт только его срез — виджет не видит чужие данные.
- **SWR** (stale-while-revalidate — «устаревшее-пока-обновляется», механизм —
  TanStack Query): при смене фильтра из кэша мгновенно отдаются предыдущие
  данные (`refreshing`), а свежие подтягиваются фоновым запросом — интерфейс
  не мигает и не показывает skeleton поверх контента.
- **Контент не исчезает после первой загрузки.** Skeleton — только Initial
  loading (`data === null`, данных ещё никогда не было). При смене фильтра
  на период, которого нет в кэше, хук удерживает данные предыдущего запроса
  (механизм — `placeholderData: keepPreviousData` TanStack Query):
  `data !== null`, `isRefreshing` — виджет продолжает показывать предыдущий
  период, нотификация «Обновление данных…» (`ui.md`, «Loading при смене
  периода»: старый контент остаётся видимым). Результат запроса попадает
  в кэш — возврат к этому периоду потом мгновенный.
- Hooks не форматируют значения и не считают метрики; отдают app-типы
  (`Delta`, `Dataset<T>`, `Contribution` — `ui.md`).

Контракт хука блока — ровно три состояния (`ui.md`):

```ts
type BlockState<T> = {
  data: T | null;        // null → skeleton (первого ответа ещё не было)
  isEmpty: boolean;      // данные получены, но блок пуст (правила ui.md) → empty-слот
  isRefreshing: boolean; // фоновое обновление поверх данных (модификатор контента)
};

function useTopCustomers(): BlockState<CustomerTopData>;
function useRecentSales(): BlockState<RecentSalesData>;
```

Выбор слота тривиален и ошибок не знает: `data === null` → skeleton;
`data !== null && isEmpty` → empty; иначе → content (`isRefreshing` — не
отдельный слот, а модификатор: dimming / плавная подмена).

- `isEmpty` вычисляется хуком — правила «что считать пустым» живут в одном
  месте; виджет не анализирует данные.
- **Виджет не знает об ошибках.** Ошибка не меняет то, что рисует карточка
  (`ui.md`: 3A — «skeleton всё ещё виден», 3B — «показывается последнее
  загруженное состояние»); знание об ошибке нужно только странице — тостам.
  Ошибка конвертируется в `hasError` внутри `hooks/domain` (`DashboardError`
  — внутренняя деталь слоя, наружу из domain торчит boolean).

Статус для тостов — тот же `useDashboard`:

```ts
type DashboardStatus = {
  hasData: boolean;      // успешно получен хотя бы один ответ
  isLoading: boolean;    // первый запрос в полёте
  isRefreshing: boolean; // фоновое обновление (toast «Обновление данных…»)
  hasError: boolean;     // последняя попытка не удалась
  retry: () => void;     // единственная точка повтора — виджет toasts
};
```

Различение 3A/3B — по комбинации флагов (`ui.md`, «Ошибка API»):

- `hasData && hasError` → 3B: toast «Не удалось обновить данные. Показаны
  данные за предыдущий период» + «Обновить»;
- `!hasData && hasError` → 3A: toast «Не удалось загрузить данные» + «Обновить»
  (карточки сами при этом показывают skeleton — им статус не нужен).

`retry` — единственный способ повторить запрос; вызывается только из виджета
`widgets/toasts/` (кнопка «Обновить»): путь `toasts → useDashboard → api`,
мимо карточек. Error-слот карточки не существует — у `BlockShell` ровно три
сло́та: skeleton / empty / content.

### ui/

Хуки для декомпозиции сложной логики представления. Доступны `widgets` и `components`; не знают о API, кэше и URL.

Примеры: `useDisclosure` (раскрытие), `useAnimatedCounter` (счётчик), `useHoverGroup` (группа hover-подсветки).

## 6. Слой widgets

Виджет = блок `ui.md` (11 виджетов). Каждый виджет:

- вызывает **свой** domain-hook и рендерит через общий каркас карточки
  (`BlockShell`) одно из состояний: skeleton / empty / content;
- владеет локальными состояниями: активный датасет переключателя метрик
  (смена без перезапроса — `ui.md`), hover и подсветка (например, донат ↔ легенда);
- хранит конфиг блока: подписи, состав KPI-карточек, семантику цвета Δ
  («плохая» метрика — рост красный), порядок датасетов;
- работает независимо: empty/error одного блока не влияет на другие (`ui.md`).

Виджет не знает о URL, fetch, DTO, кэше и об ошибках; его входами являются
только `BlockState` и его собственный локальный state.

**Инфраструктурные виджеты** (не блоки `ui.md`, рендерятся страницей):

- `widgets/toolbar/` — глобальные фильтры; контракт — раздел 4 (render-only
  компонент + сборка `DashboardQuery` из событий);
- `widgets/toasts/` — уведомления страницы. Подписан на `useDashboard`
  (`DashboardStatus`), конвертирует статус в тосты: `isRefreshing` →
  «Обновление данных…», `hasError` → 3A/3B-текст (по `hasData`), кнопка
  «Обновить» вызывает `retry()`. Дедуплицирует повторы и скрывает тост при
  разрешении состояния. Рендерит через примитив `components/ui/Toast`.

## 7. Слой components

Чистые render-only компоненты: рендер — функция props; никаких запросов,
контекстов и URL. Форматирование — часть отображения и живёт здесь
(`ui.md`: компонент приводит сырые числа к виду — разделители, знак U+2212,
`%` / `п.п.`, `—`). UI-хуки (`useDisclosure`, `useAnimatedCounter`,
`useHoverGroup`) — из `hooks/ui/`; доменные хуки (`hooks/domain/`) — недоступны.

Категории внутри `components/` — строго по назначению элемента, шаблонов
страниц здесь нет:

- примитивы `ui/`: `Card`, `Badge`, `Skeleton`, `Avatar`,
  `SegmentedControl` (тулбар пресетов и сегмента собран из них в `ui/`),
  `Tooltip` (hover-логика + `@floating-ui/react-dom` для позиционирования),
  `Toaster` (точка настройки `<Toaster>` из sonner);
- элементы данных `data/`: `DeltaBadge`, `ContributionBar`, `Sparkline`,
  строки списков;
- графики `charts/` — обёртки библиотеки графиков (props in → чарт).

Skeleton повторяет форму реального контента (`ui.md`, «Initial loading»); у
каждого блока — свой skeleton-компонент. Микроанимации (появление карточек,
animated counters, переходы графиков) — внутри `components`; данные они не меняют.

## 8. Слой api

- Единственный вызов: `POST /api/v1/dashboard` с телом `{ from, to, segment? }`
  (`api.md`).
- **Подстановка раскрытых границ** — здесь: `from` / `to` из URL раскрываются
  в `from 00:00:00Z … (to + 1 день) 00:00:00Z` (чистая функция `utils/dates.ts`)
  и подставляются в тело запроса перед отправкой.
- Типы ответа (DTO из `api.md`) — источник правды на этой границе; маппинг в
  app-типы (`ui.md`) выполняется здесь, глубже транспортные числа не ходят:

| DTO (`api.md`) | App (`ui.md`) |
|---|---|
| `DeltaUnit`: `1` / `2` | `'percent'` / `'pp'` |
| `ContributionUnit`: `1…4` | `'gp'` / `'revenue'` / `'units'` / `'ac'` |
| `SaleStatus`: `1…3` | `'paid'` / `'refunded'` / `'cancelled'` |
| `Segment`: `1…3` | `'enterprise'` / `'mid-market'` / `'smb'` |

- Ошибки: `ProblemDetails` (400/500) и сетевые сбои приводятся к единому
  `DashboardError` — внутренней дета́ли границы `api → hooks`; наружу из
  domain-слоя торчит только boolean (`hasError`), UI-типов ошибок нет.
- Слой не знает о React, кэше и состояниях интерфейса.

## 9. Поток данных

### Контракт виджета (вход/выход)

Каждый из 11 виджетов — чёрный ящик с одинаковым контрактом. Детали блоков
(датасеты, hover, подписи) — внутренние, наружу торчат только потоки ниже.

```
                            КОНТРАКТ ВИДЖЕТА

 ┌─────────┐  DTO   ┌──────────────┐ BlockState<T> ┌────────┐ props ┌────────────┐
 │ backend │ ─────► │ hooks/domain │ ────────────► │ виджет │ ────► │ components │
 └─────────┘        └──────────────┘               └────────┘       └────────────┘
      POST /api/v1/dashboard       свой хук         вход: данные  props in → JSX out
      → маппинг в app-типы         на блок          + состояние   (не детализируем)

   Данные (вход виджета)            События (выход виджета)
   ─────────────────────            ────────────────────────
   BlockState<T>:                   callback-события → widgets/toolbar → page.tsx
      data                          (тулбар)           → router.replace → URL
      isEmpty                       всё остальное    → локальный state виджета
      isRefreshing                                     (датасет, hover) — наружу
                                                       не выходит
```

Виджет **получает**: срез данных блока через свой domain-hook (`BlockState<T>`)
и ничего больше — ни URL, ни DTO, ни кэша, ни ошибок. Виджет **отдаёт
наружу**: только выбор пользователя в виде callback'ов для page (тулбар);
во всех остальных случаях события остаются внутри виджета (локальный state).
Компоненты не детализируем: props in → JSX out. Ошибки и `retry` — не часть
контракта виджета: они в `DashboardStatus`, который потребляет только виджет
`widgets/toasts/`.

### Потоки данных

| Поток | Маршрут | Что течёт |
|---|---|---|
| Данные блока | `api → hooks/domain → widget` | `DashboardDto` → маппинг → app-типы → срез `BlockState<T>` |
| Состояние блока | `hooks/domain → widget` | `data` / `isEmpty` / `isRefreshing` — виджет выбирает слот `BlockShell` |
| Статус запроса | `hooks/domain → widgets/toasts` | `DashboardStatus` (`useDashboard`) → тосты 2 / 3A / 3B |
| Действие «Обновить» | `widgets/toasts → hooks/domain` | `retry()` из тоста «Обновить» → повторный запрос; карточки не участвуют |
| Выбор фильтра | `toolbar-компонент → widgets/toolbar → page.tsx → hooks/app → router.replace → URL` | события компонента → сборка `DashboardQuery` → запись в URL |
| Изменение фильтров | `hooks/app → DashboardQueryContext → hooks/domain → виджеты` | `page.tsx` оборачивает дерево в `DashboardQueryContext`; domain-hooks читают `query` из контекста и включают его в ключ кэша `[from, to, segment]`; виджеты узнают об изменениях фильтров **опосредованно** — через изменившийся `BlockState` своего хука, сами контекст не читают |
| Локальный выбор виджета | внутри виджета | активный датасет, hover — state виджета; в поток данных не попадает |

| Событие | Что происходит |
|---|---|
| Первая загрузка | `page.tsx` читает URL (`useDashboardQuery`) → query в контексте → hooks запрашивают → виджеты показывают skeleton → контент |
| Смена периода / сегмента | тулбар → `router.replace` → новый query → если новый период в кэше — данные сразу из кэша; иначе хук удерживает данные предыдущего периода (`keepPreviousData`) → `isRefreshing` → toasts показывают «Обновление данных…» → фоновый запрос → плавная замена контента |
| Смена на период, которого нет в кэше | как обычная смена периода: показываются данные предыдущего периода + `isRefreshing` + toast «Обновление данных…»; результат попадает в кэш |
| Возврат к ранее выбранному периоду | данные мгновенно из кэша, фоновое обновление |
| Переключение метрики (датасета) | локальный state виджета; запроса нет |
| Ошибка при первой загрузке (3A) | карточки на skeleton (`data === null`) + `hasError` → toasts «Не удалось загрузить данные» + «Обновить» |
| Ошибка при обновлении (3B) | карточки показывают старые данные + `hasError` → toasts «Не удалось обновить данные…» + «Обновить» |
| Пустой период | данные получены; каждый блок рендерит empty-состояние (`ui.md`) |

## 10. Состояния интерфейса

| Состояние (`ui.md`) | Владелец | Механизм |
|---|---|---|
| Initial loading | `widgets` | skeleton-слот `BlockShell` (`data === null`) |
| Loading при смене периода | `hooks` + `widgets/toasts` | данные предыдущего периода сохраняются (`isRefreshing`, `keepPreviousData`), toasts «Обновление данных…» |
| Ошибка API (3A / 3B) | `widgets` + `widgets/toasts` | карточки по `BlockState` (skeleton / старые данные — без знания об ошибке); тип тоста — `DashboardStatus.hasError` + `hasData`; повтор — `retry()` из тоста |
| Пустой период | `widgets` | empty-слот; «Потери» — свои заглушки (`ui.md`) |
| Нет данных по отдельному блоку | `widgets` | empty-слот, независимо от других блоков |

## 11. Тестируемость

Тестируем только логику: хуки, сервисы (`api`), утилиты (`utils`). Компоненты
и виджеты **не тестируем** — render-only JSX не содержит ветвящейся логики,
его проверяет ручная проверка по состояниям (`ui.md`) и review. Форматирование
чисел при этом всё равно покрыто: оно живёт в `utils`, а не в компонентах.

| Уровень | Что проверяется (`specification.md`, §12) |
|---|---|
| `utils` | форматирование чисел и дат, раскрытие границ дня (юнит, без DOM) |
| `app` (url-сервис) | парсинг, валидация и нормализация URL, round-trip parse ↔ write (юнит, без DOM) |
| `api` | подстановка раскрытых границ, приведение enum'ов, типизация ошибок (юнит, без DOM) |
| `hooks` | маппинг DTO → app-типы, ключ кэша, `BlockState` (юнит, без DOM) |
| `app` | смена периода → навигация + новый запрос (интеграционно, с моком сети) |

## 11.1. Комментарии в коде

Кодовые комментарии — на **русском языке**, для каждой функции, метода и
класса. Минимальное содержимое — описание аргументов; максимальное —
объяснение «хитрой» логики и её связей с доменом/UI-архитектурой.

**Обязательный минимум (любая функция/класс):**

- назначение сущности — одна строка по-русски;
- описание каждого аргумента: что означает, ограничения, что происходит при
  `null`/`undefined`/пустом значении (если применимо);
- возвращаемое значение, если его смысл не очевиден из имени и типа.

**Дополнительно — когда логика «хитрая» (неочевидная, с контрактами):**

- **Ссылки на домен (`domain.md`, `api.md`)** — обязательны там, где логика
  повторяет или реализует правило домена. Примеры:

  ```ts
  /**
   * Раскрывает границы дня в UTC-полуинтервал [from, to):
   * from → 00:00:00Z, to → (to + 1 день) 00:00:00Z.
   *
   * Верхняя граница исключается — см. domain.md, «Активный период».
   */
  function expandDayBoundaries(from: IsoDay, to: IsoDay): UtcRange;
  ```

- **Ссылки на UI-архитектуру (`ui.md`, `frontend.md`)** — обязательны там,
  где код реализует правило слоёв или поведение интерфейса. Примеры:

  ```ts
  /**
   * Возвращает слот для рендера по правилам ui.md, «Empty-состояние»:
   * data === null → skeleton; data не null и пусто → empty; иначе content.
   *
   * isEmpty вычислен хуком (правила пустоты — в одном месте, виджет
   * их не анализирует — frontend.md, раздел 5).
   */
  function selectBlockSlot<T>(state: BlockState<T>): BlockSlot;

  /**
   * Конвертирует DashboardStatus в тосты. Различение 3A/3B — по
   * hasData + hasError (frontend.md, раздел 5; ui.md, «Ошибка API»):
   * hasData && hasError → 3B, !hasData && hasError → 3A.
   */
  function buildToastFromStatus(status: DashboardStatus): ToastCommand | null;
  ```

- **Инварианты и «неочевидное»** — фиксируются у места возникновения:
  почему нельзя иначе, что сломается при нарушении. Пример:

  ```ts
  /**
   * Ключ кэша — ровно [from, to, segment]; другие поля query в ключ не
   * входят: датасеты и hover — локальный state виджетов (frontend.md,
   * раздел 4), в кэш не влияют.
   */
  function buildCacheKey(query: DashboardQuery): CacheKey;
  ```

**Чего не пишем:**

- перефразирование типов и имён («функция возвращает число» для
  `(): number`);
- истории («добавлено 05.10», «исправлено по задаче...») — история в git;
- `//` в одну строку для многошагового объяснения — только JSDoc-блоки
  (`/** */`) для публичных контрактов, `//` допустим для локальных заметок
  внутри тела (не для контрактов).

## 12. Сознательно не делаем

- Глобальный стор (Redux/Zustand) — серверные данные живут в кэше запроса,
  UI-состояние локально; стор дублировал бы оба источника.
- Запрос на блок — контракт `api.md` предполагает один запрос на весь дашборд.
- SSR/RSC-данные и Server Actions — дашборд интерактивный, переходы периодов
  обслуживает клиентский кэш в режиме stale-while-revalidate (TanStack Query);
  второй путь загрузки дублировал бы состояния.
- Состояние датасетов в URL — это не глобальный фильтр (`ui.md`); хранение
  табов в localStorage/cookie тоже сознательно отвергнуто (SSR-рассинхрон
  ради второстепенной настройки) — табы живут в памяти виджета и сбрасываются
  при перезагрузке.
- Мобильная адаптация (`specification.md`, §20).

| Позиционирование поповеров | `@floating-ui/react-dom` (только движок позиционирования) | Рукописный tooltip (позиционирование кажется тривиальным, но: flip у краёв, follow за скроллом в скроллящихся списках — наш топ-10, ресайз, offset под курсор, `aria-describedby` — постоянная полировка вместо задачи), `@floating-ui/react` (полный, с interactions — свой store для open-state, +8 kB ради hover'а в 4 строки), radix-ui Tooltip (runtime-провайдеры конфликтуют с render-only слоем, стр. 102), CSS Anchor Positioning (нативная замена, но Firefox/Safari ещё не поддерживают) | Движок — фактический стандарт (тултипы MUI стоят на нём); flip/shift/offset + `autoUpdate` (следит за скроллом/ресайзом) из коробки; ~2–3 kB, tree-shakeable, хуки без провайдеров — дружит с render-only. Hover-логика (4 строки) — в примитиве `components/ui/Tooltip.tsx`. **План отказа:** когда CSS Anchor Positioning дописывает кросс-браузерность — заменяем на нативку и сносим зависимость |
| Примитивы UI | рукописные (`components/ui/`) | radix-ui primitives, React Aria Components (оба — runtime-провайдеры и обёртки ради пары сценариев) | Инвентарь сценариев мал: tooltip (2 кейса — бейдж, строка) — см. строку про Floating UI; чарт-tooltip — штатный у recharts; toast-рендер — `<Toaster>` sonner. Остаётся SegmentedControl (radio-семантика, roving tabindex, стрелки — ~40 строк известного паттерна) и чистый div+CSS (`Card`, `Badge`, `Skeleton`, `Avatar`); библиотека примитивов ради одного SegmentedControl не окупается |
| Стили | `tailwindcss` v4 | CSS Modules (тяжелее поддерживать дизайн-систему в одном месте), styled-components (runtime CSS-in-JS, минус для SSR и для render-only компонент) | v4 — CSS-first конфиг (`@theme`), design tokens в CSS без JS-сборки; с render-only компонентами работает без перекрещивания runtime; официальный рецепт Next.js (шаблоны App Router создаются с ним по умолчанию) |
| HTTP-клиент | `fetch` (native) | axios (XSRF/interceptors не нужны, вес лишний), ky (лишний слой над fetch) | Один POST, без авторизации, без interceptors; `AbortController` для retry/cancel — нативно; типизация DTO — генерируем/пишем руками в `types/dto.ts` |

**Дополнительно:**

- **`zod` + `openapi-typescript`** (build-time) — валидация DTO на границе `api`
  и синхронизация типов с `api.md` без ручного дублирования. Альтернатива —
  голые TS-типы, но тогда рассинхрон с `api.md` ловится только на тестах.
- **Без `zustand`/`redux`** — решение из раздела 12 не меняется.
- **Без `react-query` devtools в проде** — dev-only импорт.
- **Next.js data layer (RSC, Server Actions, fetch-cache в RSC) — не
  используем**: интерактивный SPA-подобный экран обслуживает клиентский кэш;
  второй серверный путь загрузки дублировал бы состояния (раздел 12).

**Что осознанно НЕ включено:** storybook (страница одна, ручная проверка по
`ui.md`), design-system-пакеты (MUI/Ant — тянут свою дизайн-надстройку и
конфликтуют с render-only компонентами), библиотеки примитивов
(radix-ui/React Aria — см. строку «Примитивы UI»), локализация (интерфейс на
русском, даты/числа форматируются в `utils/format.ts` руками).
