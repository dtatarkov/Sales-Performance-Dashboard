# Sales Performance Dashboard — frontend

Дашборд продаж: Next.js (App Router) + TypeScript + TanStack Query +
Recharts + sonner. Desktop-страница одна (целевой viewport 1440×900):
11 блоков дашборда, все данные приходят с сервера одним ответом
`POST /api/v1/dashboard` — клиент метрик не считает, только отображает.

Правила организации кода и стиля — `AGENTS.md` (корень репозитория).
Бизнес-правила — `docs/domain.md`, требования — `docs/specification.md`.
Этот README самодостаточен для ежедневной работы: архитектура слоёв,
URL-контракт, контракт API и UI-правила описаны здесь.

## Стек

| Зона | Библиотека |
|---|---|
| Каркас | Next.js (App Router), TypeScript, Tailwind v4 |
| Серверное состояние | TanStack Query v5 (кэш, stale-while-revalidate) |

| Тосты | sonner |

| HTTP | нативный `fetch` |

## Принципы

- **Один запрос — весь дашборд.** `POST /api/v1/dashboard` вызывается один
  раз на набор фильтров; блоки не делают собственных запросов.
- **Однонаправленные зависимости.** Рендер — `app → widgets → components`;
  данные — `widgets → hooks → services/api`. Обратных и боковых импортов
  нет — запреты закреплены import-boundaries линтером.
- **URL — источник правды глобальных фильтров** (период, сегмент).
  Остальное (активный датасет, hover) — локальное состояние виджета,
  эфемерное: сброс при перезагрузке — ожидаемое поведение.
- **Единый контракт состояний блока**: skeleton / empty / content,
  `isRefreshing` — модификатор поверх контента. Каждый блок отображает
  своё состояние независимо от остальных.
- **Данные — сырые числа, форматирование — на компоненте.** Разделители,
  U+2212, `%`/`п.п.`, `—` — забота `formatters/` и компонентов.
- **Бизнес-логики на клиенте нет.** Значения, Δ, доли, вклады,
  ранжирование и пороги приходят вычисленными с сервера.

## Слои и поток данных

```
URL → hooks/app (useDashboardQuery) → contexts (DashboardQueryContext)
    → hooks/domain (useDashboard + хук блока) → BlockState<T> → виджет
    → components → formatters
```

| Слой | Роль |
|---|---|
| `app/` | Только `layout.tsx` + `page.tsx`: страница читает URL и публикует `query` в контекст, компонует виджеты. Локального JSX нет |
| `widgets/` | 11 блоков дашборда (1 блок = 1 виджет) + инфраструктурные `DashboardToolbarWidget`, `ToastsWidget`. Вход — `BlockState<T>`; владеют локальными состояниями (датасет, hover) и конфигом блока |
| `hooks/` | `app/` — граница URL; `domain/` — доступ к данным; `ui/` — логика представления (`useDisclosure`, `useAnimatedCounter`, `useHoverGroup`, `useScrollFade`) |
| `contexts/` | `dashboardQueryContext` (глобальные фильтры), `queryProvider` (обёртка `QueryClientProvider`) |
| `services/` | Оркестрация запроса: сборка тела (раскрытые границы дня), вызов клиента, маппинг ответа |
| `api/` | HTTP-клиент и выполнение запроса (`client.ts`, `request.ts`) |
| `mappers/` | Маппинг DTO → app-типы, по блоку (`mapDashboard`, `kpi`, `dataset`, `enumMappers`, …) |
| `parsers/` | Парсинг сырых значений DTO с сообщениями об ошибках (`parseDate`, `parseNumber`, `parseEnum`) |
| `errors/` | Типы ошибок API, парсинг `ProblemDetails`, форматирование (`apiError`, `parseError`, `formatError`) |
| `components/` | Render-only: `ui/` (Card, Avatar, DateRangePicker, Toaster…), `data/` (DeltaBadge, DeltaText…), `charts/` |
| `formatters/` | Форматирование для показа: деньги (шкала тыс/млн), проценты, даты, Δ, вклад |
| `types/` | Только типы данных: DTO, формы метрик (`Delta`, `Dataset<T>`, `Contribution`) |
| `interfaces/` | Публичные контракты модулей (`DashboardQuery`, `BlockState`, `DashboardStatus`) |
| `configuration/` | Дефолты, пресеты, палитра, env (`dashboard.ts`, `colorPalette.ts`, `env.ts`) |
| `mocks/` | Мок-данные тестов и стендов |

Ключевые правила зависимостей (полный список — `AGENTS.md`): виджеты
не импортируют `api/*` и `next/*`;
компоненты render-only — без доменных хуков, API, URL и контекстов;
`next/navigation` только в `hooks/app` и каркасе; единственный, кто читает
и пишет `searchParams` — `hooks/app/useDashboardQuery`.

## Ключевые контракты

```ts
// interfaces/ — контракт виджета (3 состояния):
type BlockState<T> = {
  data: T | null;        // null → skeleton (первого ответа ещё не было)
  isEmpty: boolean;      // данные получены, но блок пуст (правила пустоты — в хуке)
  isRefreshing: boolean; // фоновое обновление поверх данных
};

// interfaces/ — статус запроса для тостов (потребляет только ToastsWidget):
type DashboardStatus = {
  hasData: boolean;      // успешно получен хотя бы один ответ
  isLoading: boolean;    // первый запрос в полёте
  isRefreshing: boolean; // фоновое обновление
  hasError: boolean;     // последняя попытка не удалась
  retry: () => void;     // единственная точка повтора — кнопка в тосте
};

// interfaces/ — глобальные фильтры:
type DashboardQuery = {
  from: IsoDate;                    // YYYY-MM-DD
  to: IsoDate;                      // YYYY-MM-DD, включительно
  segment: CustomerSegment | null;  // null — все сегменты
};
```

- **Кэш один на всё приложение** — ключ `[from, to, segment]`; хук блока
  отдаёт селектором только свой срез. Механизм — TanStack Query:
  SWR-поведение и `placeholderData: keepPreviousData`.
- **Контент не исчезает после первой загрузки.** Skeleton — только когда
  `data === null`; при смене периода хук удерживает данные предыдущего
  запроса (`isRefreshing`), появляется тост «Обновление данных…», затем
  плавная замена. Возврат к ранее выбранному периоду — мгновенно из кэша.
- **Виджет не знает об ошибках.** Карточка при ошибке продолжает показывать
  skeleton или последние данные; знание об ошибке нужно только тостам.
  Различение: `!hasData && hasError` → 3A «Не удалось загрузить данные»;
  `hasData && hasError` → 3B «Не удалось обновить данные. Показаны данные
  за предыдущий период» — обе с кнопкой «Обновить» (`retry()`).
- **Переключение датасета — без запроса**: все датасеты приходят
  одновременно, виджет лишь выбирает активный. Табы в URL/localStorage
  не сохраняются.

## URL-контракт

Маршрут `/`; глобальные фильтры в `searchParams`:

| Параметр | Формат | Смысл |
|---|---|---|
| `from` | `YYYY-MM-DD` | Начало периода |
| `to` | `YYYY-MM-DD` | Конец периода, **включительно** |
| `segment` | `enterprise` / `mid-market` / `smb` | Отсутствует — все сегменты |

- Отсутствующие и невалидные параметры нормализуются к дефолтам
  (`configuration/dashboard.ts`: пресет `30d`, все сегменты); невалидный
  `from > to` нормализуется. Логика — в `hooks/app/useDashboardQuery.ts`.
- Запись — `router.replace` (без перезагрузки и засорения истории).
- Пресеты (`today`, `7d`, `30d`, `this-month`, `last-month`) вычисляются
  на клиенте в UTC; «произвольный период» — отдельный режим.
- В запрос к API границы раскрываются чистой функцией
  `utils/expandDayBoundaries`: `from 00:00:00Z … (to + 1 день) 00:00:00Z`
  — полуинтервал `[from, to)`.

## Контракт API (что ожидает клиент)

Существенное для клиента:

- `POST {API_BASE_URL}/api/v1/dashboard`, тело `{ from, to, segment? }` —
  целодневные границы UTC (иначе `400 PERIOD_NOT_DAY_ALIGNED`).
- **Enum'ы числовые**, маппятся в строки-литералы в `mappers/enumMappers`:
  `Segment` `1/2/3` → `enterprise/mid-market/smb`; `DeltaUnit` `1/2` →
  `percent/pp`; `ContributionUnit` `1…4` → `gp/revenue/units/ac`;
  `SaleStatus` `1…3` → `paid/refunded/cancelled`.
- **`null` ≠ `0`**: `null` — «не определено» (пустой знаменатель, малая
  выборка) → показываем `—`; `0` — реальный ноль → `0 ₽`. `delta: null` —
  Δ не вычисляется.
- **Точка серии несёт полуинтервал `dateFrom`/`dateTo`** (сетка бакетов:
  делитель длительности, ближайший к «длительность / 30», полоса [24, 36]
  точек). Ось «Динамики во времени» подписывает уникальные дни, тултип
  показывает диапазон бакета; спарклайны диапазон не показывают.
- **Ошибки** — `ProblemDetails` с `errors[] {field, code}`; коды
  `PERIOD_REQUIRED`, `PERIOD_INVALID_ORDER`, `PERIOD_NOT_DAY_ALIGNED`,
  `SEGMENT_INVALID`; `500` без деталей. Типы ошибок разделены по причине —
  `ApiError` (транспорт/HTTP), `ParseError` (рассинхрон контракта),
  `FormatError` (невозможно отформатировать значение), все в `errors/`;
  наружу из domain-слоя торчит только boolean `hasError`.

## UI-правила

Сквозные правила:

| Ситуация | Результат |
|---|---|
| Метрика не определена (пустой знаменатель, малая выборка) | `—` — не `0`, не `0%` |
| Реальный ноль | `0` / `0 ₽` |
| Отрицательное значение | `−x` — U+2212, не дефис |
| Δ метрики-доли (маржа, доли возвратов/отмен) | в **п.п.**; остальных — в `%` |
| Цвет Δ | по **семантике метрики**: у «плохих» (возвраты, отмены) рост — красный |
| Цвет датасета | по позиции в переключателе: 1-й — синий, 2-й — зелёный, 3-й — оранжевый |
| Цвет строки рейтинга / сегмента доната / точки легенды | по **позиции** в списке (`paletteColorOf(index)`, `categoryColorOf(index)`): цвет закреплён за позицией, не за элементом — цвет это индикатор позиции, а не идентификатор. Решение уровня всего дашборда: привязка к имени/id давала бы «перетасовку» цветов при каждой пересортировке (смена метрики, периода) — ререндер и скачки |
| Ключи строк списков | `index`: строки не размонтируются при смене датасета/периода — бар и вклад перетекают prev → current (`useTransitionValue`), новые строки «въезжают», а не появляются. Секции динамики дополняются null-слотами до фиксированного топа. Списки без анимаций (лента продаж, легенда категорий) используют содержательный ключ |

- **`Delta`** — `{ value, unit }`; стрелка `▲`/`▼` из знака, суффикс из
  `unit`, `null` → `—`. Форматирование — `formatters/formatDelta`.
- **`Contribution`** — `valueAbsolute` (крупное число), `valueRelative` +
  `valueRelativeUnit` (подпись: `26,2% от ВП`, `1,7× к СЧ`, …),
  `valueNormalized` (бар 0–100, готовый).
- **Макет**: 12 колонок; ряды — KPI (6 компактных карточек) → пары
  стандартных карточек «кто продаёт» → «кому продаём» → «как меняется» →
  «что продаём» → «что ушло» (потери, уменьшенный типоразмер). Высота
  карточки задаётся типоразмером, а не содержимым — загрузка и смена
  периода не двигают сетку. Скролл — внутри карточки, с fade внизу.
- **Тулбар**: sticky; период слева (пресеты + «Произвольный период» +
  вторая строка с активным диапазоном и длительностью), сегмент справа.
  Повторный клик по активному сегменту снимает выбор; ширина кнопки
  при переключении не меняется.
- **Скелетоны повторяют форму контента** (строки списков, зона графика,
  зона доната), не абстрактные блоки.

## Блоки (11)

| Блок | Ключевое |
|---|---|
| KPI (6 карточек) | Выручка, ВП, маржа, продажи, СЧ, «Лучший менеджер»; Δ-бейдж + спарклайн |
| Рейтинг менеджеров | 2 уровня строки; бар из `valueNormalized`; вклад; доля отмен; скролл внутри |
| Сравнение менеджеров | Горизонтальный bar-chart, топ-10 по активной метрике, менеджеры по Y |
| Клиенты — Топ-10 | Список как рейтинг; `клиент с {since} · N заказов`; возвраты и отмены уровнем 2 |
| Динамика клиентов | Дивергентные бары от нулевой линии, секции «Рост»/«Падение» (Dyn Top N), сортировка по абсолютной Δ |
| Динамика во времени | Area-чарт: сплошная — активный период, пунктир — предыдущий |
| Продажи по категориям | Донат + легенда-таблица со скроллом; hover связывает сегмент ↔ строку; центр — сумма |
| Лучшие продукты | Топ-10, 3 датасета; строка 2-го уровня — 5 метрик с Δ |
| Последние продажи | Лента сделок со статус-бейджем; **итоговой строки нет** (числа потерь — только в блоках потерь) |
| Возвраты | Разрез — товары; топ + хвост «Остальные N» до 100% группы |
| Отмены | Разрез — менеджеры; аналогично возвратам |

Жёсткие правила потерь: возвраты и отмены — **два независимых блока**,
никаких «всего потерь» и общих Δ; разрез не переключается; нет продаж —
`0 ₽` + «Возвратов нет» (реальный ноль, не `—`); доля не определена — `—`.

## Запуск и проверки

```bash
npm run dev            # http://localhost:3000; нужен запущенный backend
```

- `API_BASE_URL` берётся из `NEXT_PUBLIC_API_BASE_URL`
  (`configuration/env.ts`); браузер ходит к API напрямую, в Docker образе
  URL инлайнится при сборке (`docker-compose.yml`).
- Проверки после задачи (`AGENTS.md`): `npx tsc --noEmit` →
  `npm run lint` → целевые `vitest` → `curl localhost:3000`.
- Тестируется логика: хуки, сервисы, мапперы, парсеры, форматтеры,
  утилиты. Компоненты и виджеты — render-only, их проверяет ручная
  приёмка по состояниям (все пять глобальных состояний: initial loading,
  обновление, ошибки 3A/3B, пустой период, частичные данные).
